## 2. How the output works

### 2a. One enquiry end to end (code reading, no live run)

**CLI `afs-assist assess --text …`**
1. `cli.py:68` `_assess` builds an `OpenRouterClient` and calls `_assess_one`.
2. `_assess_one` (`cli.py:41`) makes a unique run_id and calls `pipeline.run` (`cli.py:51`).
3. `pipeline.run` (`pipeline.py:514`) runs these steps:
   1. **Intake:** an LLM call with a strict JSON schema, then `sanitize_intake` (unquoted facts are removed). A collapsed intake is retried once (`MAX_INTAKE_ATTEMPTS`).
   2. **Off-topic short-circuit** (`is_off_topic`, `pipeline.py:121`). It needs both the model's `out_of_scope` route and no measurement cue at all.
   3. **Screen:** `slots_from_intake` → `screen.screen`. Deterministic, method × technique against the 44 rules.
   4. **Assess:** one LLM call. The system prompt is `assess_system()` (`pipeline.py:91`): prompt + skill + all 67 pages + the rules with their verbatim source quotes. The user message holds the enquiry, the intake JSON, the methods named in the enquiry and the screening table.
   5. **Verify:** `verify.verify`, about 130–160 checks per case. Quotes are checked exact or loose on the cited page, then page scope, claim-local numbers, forbidden wording and structure.
   6. **Repair:** up to 2 rounds (`MAX_REPAIR_ROUNDS`, `pipeline.py:53`). Each repair returns a complete new assessment, and the round with the fewest hard failures is kept.
   7. **Finalize** (`pipeline.py:209`): failed citations are stripped, screen-failed roles demoted, duplicates removed, the status corrected, plus the fallbacks.
   8. **External step** (`pipeline.py:598`), only after the primary result is complete. It is wrapped so a failure cannot discard the assessment.
4. `render.to_json` / `to_markdown` (`render.py:378`) build the output, `provenance.record` writes a commit on the `provenance` branch (`cli.py:56`), and the files go to `--out`.

**Chat backend**
- **New enquiry:** `ui/server.py:327` `_work` calls the same `cli._assess_one` (`server.py:336`), so the UI and CLI produce identical runs.
- **Follow-up:** `chat.ask` (`chat.py:393`, called at `server.py:357`) makes one strict-JSON call over all pages, a run digest and the stored external items.
  - `check_claim` (`chat.py:278`) checks each claim: quote, scope, external item, claim-local figures and wording.
  - One repair round follows. A claim that still fails is removed, and a "removed" line says so.
  - The UI renders the blocks from the verified run JSON; the model only names them.
- Routing is deterministic (`chat.route`, `chat.py:146`).

**Observed in the frozen runs** (`outputs/final/H0*.json`):
- Every H case needed a repair round: 1, 2, 4, 10, 6 and 4 hard failures before repair, 0 after.
- The repair took 44–130 s, which is 46–72 % of wall time.
- Because the repair returns a complete assessment and `kept_round` = 1 in 6/6, **all six shown H answers are written by the repair model (google/gemini-3.8-flash), not by the "assess" model (GLM-5.3-Flash)**. README "Models" says GLM "writes the assessment". That is true only of the first draft (see N11).
